# TrainMind 项目面试介绍指南

## 一、介绍项目时的主线

不要按照简历上的技术栈顺序逐个念。整个项目只讲两条主线：

1. Java 侧解决高并发购票、超卖、重复提交和跨服务一致性；
2. Python 侧解决自然语言查询、行程推荐、票务知识问答和多轮会话。

核心边界是：**Agent 只查询和规划，真正的下单、选座、扣库存仍由 Java 交易链路完成。**

## 二、30 秒版本

TrainMind 是一个火车票微服务与智能出行 Agent 项目，整体分为 Java 票务底座和 Python Agent 两部分。Java 侧使用 Spring Cloud 拆分会员、票务和批处理服务，并通过 Redis、RocketMQ、Redisson 和 Seata 处理高并发购票、重复提交、超卖及数据一致性。Agent 侧使用 FastAPI 和 LangGraph 实现 ReAct 工具调用，通过 MCP 查询真实车站和余票，并使用 Redis/MySQL 保存多轮会话；票务规则问题通过 pgvector 混合 RAG 检索。Agent 只负责查询和推荐，交易操作仍由 Java 服务完成。

## 三、90 秒推荐版本

我做的项目叫 TrainMind，它原本是一个高并发火车票微服务系统，后来我在上面增加了独立的智能出行 Agent。

Java 侧使用 Spring Cloud 拆分 Gateway、Member、Business 和 Batch 服务，Nacos 负责注册和配置，Gateway 统一做路由与鉴权，OpenFeign 完成服务间调用。购票场景最大的难点是瞬时流量、重复请求和超卖，所以我先用 Redis 秒杀令牌和幂等键做前置拦截，再通过 Sentinel 限流，将请求投递到 RocketMQ 异步排队；消费者按日期和车次获取 Redisson 分布式锁后完成选座与余票扣减，并通过 Seata保证跨服务数据一致性。在 4C8G 单机环境下，JMeter 模拟 2000 并发请求时，购票受理接口达到约 700 TPS，P95 为 580ms，多轮测试没有出现重复订单和超卖。

Agent 侧使用 FastAPI 和 LangGraph 构建 ReAct 循环。大模型先理解用户的日期、站点、时间、席别和预算等约束，缺少信息时继续追问，需要数据时通过 Tool Calling 调用工具。Java 侧使用 Spring AI MCP Server 暴露车站和余票等只读工具，Python Agent 通过 MCP Client 调用，因此模型只负责决策，真实数据仍来自票务服务。Redis 保存活跃会话，MySQL保存完整聊天记录，前端通过 SSE 获取执行事件和最终结果。

规则问答使用 RAG：文档按标题和段落切分，使用 Embedding 和 pgvector 做向量检索，再和关键词检索通过 RRF 融合，最终返回 Evidence 和 Citation；如果证据不足就拒答，实时余票也不会从知识库推断。在测试集上，Agent 工具调用准确率为 94%，RAG 的 Hit@5 为 91%，Faithfulness 为 93%。

## 四、面试官让你重点讲一个难点

优先讲“为什么 Agent 不直接抢票”。

推荐回答：

大模型存在输出不稳定、响应时间较长和重复调用工具的可能，而购票链路涉及库存、订单和分布式事务，不能把写权限直接交给 Agent。因此我把 Agent 定位为查询和规划层，只通过 MCP 暴露车站、余票等只读工具。模型推荐出真实 `ticketRef` 后，前端跳转到原购票页面，用户确认后再进入 Java 的幂等、限流、消息队列和库存扣减链路。这样既利用了大模型的自然语言理解与规划能力，又不会让 Agent 的并发影响核心交易服务。

## 五、常见技术追问

### 1. LangGraph 的 ReAct 流程是什么

```text
用户消息
  → Agent Node：判断是否需要工具
  → Tool Node：调用车站、余票或知识检索
  → Observation 写回 State
  → Agent Node：继续查询、提交推荐或生成答案
  → END
```

State 中保存消息、约束、工具结果、车票目录、推荐方案和执行轨迹。没有配置大模型时，系统可以降级到规则工作流，方便本地联调。

### 2. Tool Calling 和 MCP 有什么区别

- Tool Calling：模型决定调用哪个函数，并生成结构化参数；
- MCP：规定 Agent 如何发现和调用外部工具；
- 项目中 LangGraph Agent 使用 Tool Calling 做决策，Spring AI MCP Server 负责把 Java 查询能力标准化暴露出来。

### 3. 多轮记忆怎么做

- `conversationId` 标识一段对话；
- Redis 保存活跃会话，使用滑动 TTL；
- MySQL 保存长期聊天记录和结构化约束；
- Redis 过期后可以从 MySQL 恢复；
- 用户 Token 只保存 SHA-256 指纹，不保存原始凭证。

### 4. RAG 为什么同时做关键词和向量检索

向量检索适合“火车票买了以后能不能换一天”这类口语化语义，关键词检索适合“学生票”“退票费”“儿童票”等精确词项。两路结果分数不在同一量纲，所以不直接相加，而是使用 RRF 按排名融合，兼顾语义召回和精确匹配。

### 5. 怎么减少幻觉

- 车次、余票和价格只能来自 MCP 工具；
- 推荐必须引用真实 `ticketRef`；
- 规则回答必须携带 Evidence 和 Citation；
- 检索分数低于阈值时拒答；
- 知识文档按不可信数据处理，检测 Prompt Injection；
- 实时数据与规则知识分流，禁止从 RAG 推断实时库存。

### 6. 高并发链路为什么要同时使用 Redis、MQ 和锁

- Redis 秒杀令牌：在进入业务逻辑前快速拦截无资格请求；
- 幂等键：避免用户重复提交形成多笔订单；
- Sentinel：限制入口流量；
- RocketMQ：把请求受理和耗时的选座扣库存解耦；
- Redisson：串行化同一日期、同一车次的库存修改；
- Seata：保证跨 Business、Member 服务的数据一致性。

## 六、简历指标怎么解释

### 购票指标

- 2000：JMeter 并发线程数，不等于 TPS；
- 700 TPS：测试期间每秒成功受理的请求数；
- 580ms：购票受理接口的 P95，不是完整异步订单完成时间；
- 无超卖：压测结束后核对座位、余票和成功订单数量。

### Agent 指标

- 任务完成率 88%：100 条多轮问题中，最终给出满足用户约束且引用真实车票的比例；
- 工具调用准确率 94%：模型选择正确工具且必填参数正确的比例。

### RAG 指标

- Hit@5 91%：标准相关文档出现在前 5 条检索结果中的问题比例；
- Faithfulness 93%：答案中能够被检索证据支持的事实陈述比例；
- 无依据回答率 4%：模型给出结论但无法映射到工具结果或知识证据的比例。

## 七、介绍时要避免的说法

- 不要说“我用了很多主流 Agent 技术”，要说为什么选择 LangGraph、MCP 和 RAG；
- 不要说“Agent 帮用户抢票”，它只查询和规划；
- 不要把 2000 并发说成 2000 TPS；
- 不要把 580ms 说成完整购票完成时间；
- 不要说 Redis 是长期记忆，Redis 是活跃会话缓存，MySQL 才负责持久化；
- 不要说 RAG 可以保证绝对不幻觉，只能说通过证据约束降低无依据回答。
